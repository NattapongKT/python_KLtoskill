-------------------------------------การตั้งชื่อ (Naming Convention)-------------------------------------------

ถือเป็นหนึ่งในทักษะที่สำคัญที่สุดของ Developer เพราะ "Code ถูกอ่านบ่อยกว่าถูกเขียน"
ชื่อที่ดีจะช่วยให้เราและเพื่อนร่วมทีมเข้าใจการทำงานของโปรแกรมได้ทันทีโดยไม่ต้องอ่าน Logic ทั้งหมด

1. กฎเหล็กของ Naming (The Core Principles)
    Intention-Revealing (สื่อเจตนา): ชื่อต้องบอกว่า "สิ่งนี้คืออะไร" และ "ทำหน้าที่อะไร"
    ❌ แย่: var d; // วันที่
    ✅ ดี: var daysSinceCreation;

    Pronounceable & Searchable (อ่านออกเสียงได้และค้นหาง่าย): อย่าใช้ชื่อย่อที่รู้คนเดียว หรือตัวย่อที่ค้นหาในโปรเจกต์ยาก
    ❌ แย่: const f_n = "John";
    ✅ ดี: const firstName = "John";

    Avoid Disinformation (หลีกเลี่ยงความหมายแฝงที่ผิด): อย่าตั้งชื่อที่ทำให้เข้าใจผิด
    เช่น ตั้งชื่อตัวแปรว่า userList ทั้งที่จริงๆ มันเป็น Object ไม่ใช่ List

    Consistency (ความสม่ำเสมอ): ถ้าเลือกใช้คำว่า fetch สำหรับการดึงข้อมูล ก็ควรใช้ fetch ทั้งโปรเจกต์
    ไม่ใช่เดี๋ยวใช้ get, retrieve, fetch ปนกัน

การตั้งชื่อ (Naming Convention) ถือเป็นหนึ่งในทักษะที่สำคัญที่สุดของ Developer เพราะ "Code ถูกอ่านบ่อยกว่าถูกเขียน" ชื่อที่ดีจะช่วยให้เราและเพื่อนร่วมทีมเข้าใจการทำงานของโปรแกรมได้ทันทีโดยไม่ต้องอ่าน Logic ทั้งหมดครับ

นี่คือหลักการและสิ่งที่คุณควรเรียนรู้แบ่งตามหมวดหมู่ครับ:

2. รูปแบบมาตรฐาน (Naming Cases)
ต้องเรียนรู้ว่าภาษาที่ใช้ นิยมเขียนแบบไหน ซึ่งแต่ละแบบมีชื่อเรียกเฉพาะ:
    รูปแบบ,                  ตัวอย่าง,                             การใช้งานทั่วไป
    camelCase,              "userName, calculateTotal",         "ตัวแปรและฟังก์ชัน (Java, JS, C#)"
    PascalCase,             "UserProfile, OrderService",        ชื่อ Class หรือ Component
    snake_case,             "user_id, created_at",              "Database, Python (variables/functions)"
    kebab-case,             "main-content, nav-bar",            "CSS Class, URL Path"
    SCREAMING_SNAKE_CASE,   "MAX_RETRY, API_KEY",               ค่าคงที่ (Constants)

3. การตั้งชื่อ (Naming Convention)
    สำหรับ Function / Method
    มักจะเริ่มด้วย คำกริยา (Verb) เสมอ เพราะมันคือการกระทำ:
    is... / has... : สำหรับฟังก์ชันที่ส่งคืนค่า Boolean (เช่น isValid, hasAccess)
    get... / set... : สำหรับการเข้าถึงหรือแก้ไขค่า
    handle... : สำหรับ Event ต่างๆ (เช่น handleClick)

    สำหรับ Class
    มักจะเป็น คำนาม (Noun) และใช้ PascalCase:
    ชื่อควรเจาะจง ไม่ควรตั้งกว้างเกินไป เช่น Utility (กว้างไป) → StringFormatter (ดีกว่า)

สิ่งที่ต้องเรียนรู้เพิ่มเติม (Next Steps)
Domain Driven Design (DDD) Basics: เรียนรู้ที่จะตั้งชื่อตาม "ภาษาธุรกิจ" (Ubiquitous Language)
เพื่อให้โปรแกรมเมอร์และคนทำธุรกิจคุยกันรู้เรื่อง

สรุปสั้นๆ: ชื่อที่ดีคือชื่อที่เมื่อคนอื่นมาอ่านแล้วไม่ต้องถามว่า "มันคืออะไร?"

-----------------------------------------function size-------------------------------------------------

1. กฎ 20 บรรทัด (The 20-Line Rule)
แม้ว่าจะไม่มีตัวเลขตายตัว แต่โดยทั่วไปแล้ว ฟังก์ชันไม่ควรเกิน 20-25 บรรทัด * หากฟังก์ชันยาวเกินหนึ่งหน้าจอ (ต้อง Scroll เมาส์)
แสดงว่าฟังก์ชันนั้นเริ่มซับซ้อนเกินไป ฟังก์ชันที่สั้นจะช่วยให้เราทำ Unit Testing ได้ง่ายขึ้นมาก

2. Do One Thing (Single Responsibility Principle)
ฟังก์ชันหนึ่งควรทำหน้าที่ "อย่างเดียว" และทำสิ่งนั้นให้ดีที่สุด ถ้าคุณพบว่าในฟังก์ชันมีคอมเมนต์แบ่งเป็นส่วนๆ
เช่น // step 1, // step 2 นั่นเป็นสัญญาณว่าคุณควรแยกมันออกเป็นฟังก์ชันย่อยๆ

วิธีการเช็ค: ลองอธิบายหน้าที่ของฟังก์ชัน ถ้าคุณต้องใช้คำว่า "และ" (and) เช่น "ฟังก์ชันนี้ดึงข้อมูลผู้ใช้ และ ตรวจสอบสิทธิ์
และ อัปเดต Log" แสดงว่ามันทำเยอะเกินไปแล้ว

3. ระดับของ Abstraction (One Level of Abstraction)
ในหนึ่งฟังก์ชัน โค้ดควรจะอยู่ในระดับความละเอียดเดียวกัน
High Level: เรียกฟังก์ชันอื่นมาทำงาน (เช่น validateUser(), saveToDatabase())
Low Level: โค้ดคำนวณยิบย่อย (เช่น if (user.age > 18 && user.status === 'active'))

ข้อแนะนำ: อย่าเอา High Level กับ Low Level มาเขียนปนกันในฟังก์ชันเดียว

4. จำนวน Parameter (The Rule of Arguments)
จำนวน Argument หรือ Parameter ยิ่งน้อยยิ่งดี:
0-1 ตัว: ดีมาก (Niladic/Monadic)
2 ตัว: พอรับได้ (Dyadic)
3 ตัว: เริ่มอันตราย (Triadic) - ควรพิจารณารวมเป็น Object
มากกว่า 3 ตัว: แย่ (Polyadic) - อ่านยากและทดสอบยากมาก

5. ลดการใช้ Nested Control Structures
ฟังก์ชันที่ดีไม่ควรมี if-else หรือ for-loop ซ้อนกันหลายชั้น (Nested)
พยายามให้ความลึก (Indentation) ไม่เกิน 1-2 ชั้น
ใช้เทคนิค Guard Clauses (การ Return ออกจากฟังก์ชันทันทีที่เงื่อนไขไม่ผ่าน) เพื่อลดการใช้ else ซ้อนกัน

สรุป: การเขียนฟังก์ชันขนาดเล็กไม่ใช่แค่เรื่องความสวยงาม แต่เป็นเรื่องของ Maintainability (การดูแลรักษา) ในระยะยาวครับ
